## 1. 方針
1. **屋外のスマホで読める**: 文字と背景のコントラストは 7:1 を目標にし、4.5:1 を下回らない(PM メモ3)。本文は 16px 以上。
2. **色だけに頼らない**: 状態は、色に加えて形の違うアイコンと文字のラベルで示す。白黒で印刷しても区別できる。
3. **入口は一覧**: 「何を先にやるか」が一覧の上で分かる(要対応のまとめ → フィルター → 表)。
4. **提案資料と同じ顔**: 深緑×橙(design-tokens.md の「正」)を出発点にする。LP に事例として載せたとき、資料と同じ事業者の道具に見えるようにする。
5. **部品は今あるものを使う**: shadcn/ui(Radix)と lucide-react は v1 で使っている。足したライブラリは TanStack Table(`@tanstack/react-table` 9.2.6・MIT。表の組み立て。D82)だけ。土台は UI-FOUNDATION.md の案3(D82)。
6. **ライトテーマを先に仕上げる**。ダークは後回し(§2.6)。

参考にした考え方(素材・ロゴ・固有の見た目は写していない。2026-10-03 にブラウザで公式ページを読んだ):
- デジタル庁デザインシステム β版 https://design.digital.go.jp/dads/
  - 基本デザインの構成: 色・文字・余白・角・影を土台に据える。
  - タイポグラフィ(https://design.digital.go.jp/dads/foundations/typography/): 本文と UI は 16px 以上、14px は例外。業務の画面では行の高さを詰めてよい。
- SmartHR Design System の StatusLabel https://smarthr.design/products/components/status-label/
  - 1つの対象に状態のラベルは1つ。
  - 日数のように対象ごとに違う値は、ラベルに入れずに別の場所に文字で出す。
  - 色だけで状態を伝えない。

### 2.4 文字
| 用途 | 大きさ | 行の高さ | 太さ |
|---|---|---|---|
| 画面の見出し h1 | 24px | 1.4 | 700 |
| 区画の見出し h2 | 20px | 1.4 | 700 |
| 小見出し h3 | 18px | 1.4 | 700 |
| 本文・入力欄 | 16px | 1.7 | 400 |
| 表(PC) | 15px | 1.45 | 400 |
| 補足・注記(最小) | 14px | 1.5 | 400 |
| 合計の数字 | 28px | 1 | 700 |

- 書体: 端末のゴシック(`Hiragino Sans`、`Yu Gothic UI`、`Yu Gothic`、`Meiryo`、system-ui の順)。Web フォントは読み込まない。理由: 現場の回線で表示が遅れないようにするため。
  - 提案資料の見出しは明朝(Yu Mincho)だが、画面は小さな文字が多いので明朝は使わない。LP で画面を見せるときの見出しに明朝を使うのは自由。
  - v1 は M PLUS Rounded 1c を読み込んでいる。v2 では外す案。
- 数字は等幅(`font-variant-numeric: tabular-nums`)にし、表では右に揃える。金額には「¥」と桁区切りを付け、税込か税抜かを見出しに書く。
- 入力欄の文字は 16px より小さくしない。理由: iPhone の Safari は 16px 未満の入力欄で画面を拡大してしまう。

### 2.5 余白・角・影・大きさ
- 余白: 4px 刻み(4・8・12・16・24・32・48)。カードの内側は 24px(スマホは 16px)。
- 角: ラベル 4px、ボタンと入力欄 8px、カードとダイアログ 12px。
- 影: 2段だけ。カード `--shadow-1`(ごく薄い)、浮くもの(ダイアログ・トースト・浮いたボタン)`--shadow-2`。
- 押す場所: PC・一覧は 44px 以上、現場でスマホ1分の入力は 56px 以上(`--tap-field`)。
- 幅の区切り: スマホ < 768px、タブレット 768〜1023px、PC ≥ 1024px。PC の左メニューは 232px、中身の幅は 1200px まで。

### 2.6 ダークテーマ(後回し)
- PM メモ3 により、ライトを先に仕上げる。トークンを `:root` に集めてあるので、あとで `@media (prefers-color-scheme: dark)` に同じ名前で値を足せば切り替えられる構成にしてある。
- 状態の色は、ダークでも同じ意味(青=待つ、緑=済み、橙=作業、赤茶=期限切れ)を保つ。

## 4. 部品の決まり

### 4.1 表(一覧)
- PC は表にする。列の順は「何の行か(物件・部屋/番号)→ 誰の(発注元)→ いつ → 状態 → 金額 → 気づき」。
- 行の左端の帯で、要対応の行を示す(赤茶=期日超過、橙=請求が未作成)。帯は補助で、意味は気づきの列の文字で伝える。
- 並びは「要対応を上、その中は新しい順」を基本にし、見出しで並べ替えられるようにする。並びの決まりを表の下に書く。
- **スマホ幅(768px 未満)では1行を1枚のカードにする**。
  - 1段目: 左に物件・部屋と番号、右に状態のラベル。
  - 2段目以降: 「項目名 … 値」を1行ずつ並べる。
  - 優先度の低い列(請求額・入金済み など)はカードでは省き、「残り」だけ残す。
- 空の気づきの列は、カードでは出さない。

### 4.2 フィルター
- 表の上に置く。①語句(物件名・部屋番号・内容)②選択(発注元・月)③状態のチップ(複数選択。選んだものは深緑の地+太字)。
- 件数を「10 件 / 全 48 件」の形で右に出す。
- 絞り込みの状態は URL に持つ(戻る・共有で消えない)。
- 要対応のまとめ(期日超過・請求が未作成・入金待ち)を押すと、その条件でフィルターがかかる。

### 4.3 フォーム
- 項目名は入力欄の上に置く。必須は赤茶の「必須」、任意は灰色の「任意」と書く(色だけにしない)。
- エラーは入力欄の枠を太い赤茶にし、欄の下に「何を直せばよいか」を書く。例: 「工種が選ばれていません。1つ選ぶと記録できます」(命令形の連発を避ける)。
- 金額・数量は右揃えで等幅。単価の欄には「税抜」と書く。
- 人の名前を入れてはいけない欄(メモ・依頼の内容・備考)には、欄の下に「入居者のお名前は入れません(預かる情報を減らすため)」と書く。命令形にせず、理由を添える。

### 4.4 状態の表示
- ラベルは §2.2 のとおり、1つの対象に1つ。
- 案件の画面では、8つの状態を1本の流れ(依頼 → 見積中 → 受注 → 施工中 → 完了 → 請求済 → 入金済)として上に出す。済んだ段には ✓、今の段は深緑の地にする。失注は流れの外に、点線の枠のラベルで出す。

### 4.5 ボタン
| 階層 | 見た目 | 使う場面 |
|---|---|---|
| 主 | 深緑の地+白文字 | 1つの画面に1つ(登録する・提出済にする) |
| 副 | 白地+深緑の枠 | 主の隣の別の操作(下書きを保存・CSV) |
| 文字だけ | 深緑の文字 | 付け足しの操作(見積書を見る・変える) |
| 取り消し | 白地+赤茶の枠 | 取り消す・失注にする。押すと確認を出す |
- ボタンの文字は「何が起きるか」を動詞で書く(「登録する」「完了にする」)。「OK」「はい」は使わない。

### 4.6 現場でスマホ1分の入力
- 選ぶだけで済む形を基本にし、文字を打つ欄は1行を1つまでにする。
- 選択肢は 56px 以上の大きなボタン。選ばれたものは「深緑の太い枠+薄い深緑の地+✓」で示す(色だけにしない)。
- 初期値を入れておく: 受付日・施工日は今日、発注元は物件のふだんの発注元、担当は本人。
- 「登録する」は画面の下に固定する(片手の親指で届く位置)。
- 登録したあとは、画面の下にトーストを数秒出し、次の一手(「見積を作る」)へのリンクを付ける。

### 4.7 空の状態・エラー・お知らせ・確認
- **空の状態**: 何が無いかを1文で書き、次の一手のボタンを1つだけ置く。例: 「共用部や建物全体の仕事は、まだありません。」+「部屋を選ばずに案件を登録」。
- **お知らせ**: 青(情報)・橙(注意)・赤茶(エラー)の帯。アイコン+太字の1行+説明の順に並べる。
- **確認**:
  - 取り消す・失注にする・状態を戻す操作では、ダイアログで「何が起きるか」を書いて確かめる。
  - 取り消しは、理由を書く欄を必須にする(v1 の削除理由の作法と同じ)。
  - 状態を進める提案(SPEC-v2 §3.3)は、勝手に変えずに「完了にする / このまま」の2択で出す。
- **トースト**: 黒の地に白文字。保存の結果と、取り消しや次の一手へのリンクを出す。

### 4.8 印刷(見積書)
- A4 縦、余白 15mm。画面の部品(メニュー・ボタン)は印刷しない。
- 黒と灰色だけで組み、白黒で印刷しても読めるようにする。表の見出し行は2枚目にも繰り返す。
- 見本: `form-estimate.html` の下半分。印刷した結果は `screenshots/form-estimate-print.pdf`(A4 で1枚に収まることを確認した)。

## 6. v1 から変わること(実装のときの注意)
- `globals.css` の色の変数(青系の oklch)を、この表の値に置き換える。shadcn の変数名(`--primary` など)は残し、値だけを変える。理由: 部品のコードを書き換えずに済む。
- ピンの色(`types.ts` の直書き)はトークンを参照する形に直す。
- 書体 M PLUS Rounded 1c の読み込みを外す。
- 角の丸み(`--radius` 0.9rem)を 8px に下げる。理由: 表や入力欄が多い業務の画面では、丸みが大きいと間延びして見える。

## 7. PM とユーザーに決めてほしいこと
1. 見た目の方向(深緑×橙、白い地、角は小さめ)でよいか。LP に載せる水準として足りるか。
2. 補足の文字の色を、資料の `#5C6B6D` から `#44514F` に暗くすること(資料の design-tokens.md は変えない。画面だけの値)。
3. 書体を端末のゴシックにし、Web フォントを読み込まないこと。
4. ダークテーマを後回しにすること(PM メモ3 のとおり)。
