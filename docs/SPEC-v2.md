## 0. この版でやること・やらないこと

**目的**: 1件の仕事を、依頼から入金まで1本でつなぐ。物件を軸に過去の仕事を引ける。入口は一覧とフィルター。

| やること(段階1〜4) | やらないこと(この WO の範囲外) |
|---|---|
| 物件と部屋のマスター、住所と位置 | 銀行・会計ソフトとの連携、入金の自動取り込み |
| 案件の登録・一覧・状態 | 共有リンク、見るだけの利用者、従業員ごとの権限 |
| 見積と明細(版)、原価、見積から請求へ | 訪問順、施工実績の見せ方、再訪の提案 |
| 請求の期日、未入金の一覧、出し忘れの一覧、集計、CSV、見積書の A4 印刷 | 発注元ごとの請求書の様式(段階4 の後に実ヒアリングで決める) |
| (段階5)AI の下書き。着手前に PM に設計を上げる | 写真の保存(構想ページの「その次」) |

**どの段階でも変えないこと**(feature-ideas.html と同じ):
- 金額・負担区分・承認・消し込み・送るかどうかは人が決める。画面は案を出すまで。
- 入居者名・発注元の担当者名は持たない(列も入力欄も作らない)。AI に住所・部屋番号を送らない。
- 指定アプリ・本部システムを置き換えない。
- 変更と取り消しの履歴を残す。物理削除はしない。

| 用語 | 意味 | テーブル |

## 2. 全体像

```
clients(発注元) ──┐
                   │ default_client_id
buildings(物件) ──┼── units(部屋) ── legacy_site_id ──> sites(旧・現場)
     │             │       │
     └──────── cases(案件) ┘   client_id(請求先)/ via_client_id(案1のみ)
                   │
       ┌───────────┼───────────────┬────────────┐
   estimates     jobs(施工)    invoices(請求) costs(原価)
       │                           │
 estimate_items               payments(入金)
```

- 新しいテーブル: `buildings`・`units`・`cases`・`estimates`・`estimate_items`・`costs`・`doc_counters`・`business_profile`。
- いまのテーブルに足す列: `jobs.case_id`、`invoices`(`case_id`・`estimate_id`・`due_date`・金額の内訳)、`clients`(支払条件)。いずれも NULL 可。
- いまのテーブル名とは重ならない(確認済み)。置き場所は `public` スキーマ(REBUILD-PLAN §3。PM の判断待ち)。

## 3. データモデル(案)

共通の決まり(v1 と同じ。理由は `poc-app/CLAUDE.md` §4):
- 主キーは `uuid default gen_random_uuid()`。どのテーブルも `is_deleted boolean not null default false`・`created_at`・`updated_at` を持つ(`updated_at` は既存の `set_updated_at()` トリガー)。
- **金額は税抜の整数の円**(`integer`)。計算に使う金額の列は `not null default 0`。理由: NULL が混じると合計が黙って NULL になる(db-change 原則3)。
- 選択肢は `text`+`CHECK`。ENUM は使わない。理由: 値を足すとき `alter type` が要らず、CHECK の付け替えで済む(v1 と同じ作法)。
- 人の名前を入れる列は作らない。自由記述の `memo` に入れないことは、入力欄の注記で伝える。

### 3.1 `buildings`(物件)
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `name` | text | not null | 建物名(戸建ては「○○様邸」ではなく「戸建て(大山町2丁目)」のように、人の名前を入れない形で書く。入力欄で例を示す) |
| `kind` | text | not null default '集合住宅' | CHECK: 集合住宅 / 戸建て / 店舗・事務所 / その他 |
| `address` | text | NULL 可 | 住所(番地まで)。**部屋番号は入れない**(部屋は `units`) |
| `lat`・`lng` | double precision | NULL 可 | 位置。**段階1 では入力欄を作らない**(D80)。v1 から移した物件だけ値を持つ。将来、地図や住所からの位置を足すときの受け皿 |
| `geo_source` | text | NULL 可 | CHECK: 住所検索 / 地図で指定 / 旧データ。位置の出どころを残す |
| `default_client_id` | uuid → clients | NULL 可 | この物件の仕事をふだん出す発注元。案件の登録で初期値に使う |
| `memo` | text | NULL 可 | 鍵の場所、駐車の可否など |

- インデックス: `name`(検索用)、`default_client_id`。
- 同じ建物を2回登録しないように、登録の画面で「名前が似ている物件」を先に出す(段階1)。データベースで一意にはしない(同じ名前の別の建物があるため)。

### 3.2 `units`(部屋)
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `building_id` | uuid → buildings | not null | on delete restrict |
| `room_no` | text | NULL 可 | 部屋番号。**NULL は「部屋なし」**(戸建て・店舗・共用部) |
| `legacy_site_id` | uuid → sites | NULL 可・unique | v1 の現場から移した行だけが持つ。移した元を辿るため |
| `memo` | text | NULL 可 | 間取り・型番のメモなど |

- 同じ物件に同じ部屋番号は1つ(`unique (building_id, room_no) where is_deleted = false`。NULL 同士は重複とみなさない Postgres の性質があるため、部屋なしの行が2つにならないことは画面側で確かめる)。
- 物件を登録すると「部屋なし」の行を1つ自動で作るかどうか: **作らない**。案件が部屋を指さないとき(`cases.unit_id` が NULL)を「物件全体」と読む。理由: 空の行を増やさない。

### 3.3 `cases`(案件)
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `case_no` | text | not null・unique | 例 `K2026-0042`。§3.8 の採番で振る |
| `building_id` | uuid → buildings | not null | |
| `unit_id` | uuid → units | NULL 可 | NULL は物件全体・共用部 |
| `client_id` | uuid → clients | not null | 請求先(お金を払う相手) |
| `via_client_id` | uuid → clients | NULL 可 | **案1 を採る場合だけ**(§3.10) |
| `lead_source` | text | not null default 'その他' | v1 の `sites.lead_source` と同じ CHECK |
| `work_kind` | text | not null default '原状回復' | CHECK: 原状回復 / リフォーム / クリーニング / 修繕 / その他 |
| `received_on` | date | not null default current_date | 受付日 |
| `request_summary` | text | NULL 可 | 依頼の内容(短く。入居者名は書かない) |
| `status` | text | not null default '依頼' | CHECK: 依頼 / 見積中 / 受注 / 施工中 / 完了 / 失注 |
| `lost_reason` | text | NULL 可 | 失注にしたときの理由(任意) |
| `memo` | text | NULL 可 | |

**状態の持ち方(WO の8つの状態との違いと理由)**
- WO は「依頼 → 見積中 → 受注 → 施工中 → 完了 → 請求済 → 入金済、失注」の8つ。
- v2 では、**人が動かす6つ**(依頼〜完了、失注)だけを `cases.status` に持つ。**請求済・入金済は請求と入金の行から計算する**(ビュー `case_overview` の `display_status`)。
- 理由: 請求済・入金済を列に持つと、請求を取り消したときや一部入金のときに、列と実際の請求・入金がずれる。これは D65 の「色の判定」で起きた問題と同じ形になる。計算で出せば、ずれは起きない。
- 画面では8つの状態を1本の流れとして見せる(DESIGN.md §4.4)。並び順とフィルターも8つで扱う。
- 状態を進めるのは人。ただし次の場面では、画面が「状態を進めますか」と提案する(勝手には変えない)。
  - 見積を提出済にしたとき: 見積中へ
  - 見積を採用にしたとき: 受注へ
  - 施工を記録したとき: 施工中へ
- 状態を戻す操作もできる(誤操作の訂正)。変更は監査ログに残る。

### 3.4 `estimates`(見積)と `estimate_items`(明細)

`estimates`
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `case_id` | uuid → cases | not null | |
| `estimate_no` | text | not null | 例 `M2026-0031`。版が増えても番号は同じ |
| `version` | integer | not null default 1 | 出し直すと 2, 3…。`unique (case_id, version)` |
| `copied_from_id` | uuid → estimates | NULL 可 | 前回の見積から写して作ったとき、その元(同じ案件の前の版、または別の案件の見積) |
| `status` | text | not null default '下書き' | CHECK: 下書き / 提出済 / 採用 / 不採用 |
| `issue_date` | date | NULL 可 | 提出した日 |
| `valid_until` | date | NULL 可 | 有効期限 |
| `tax_rate_pct` | integer | not null default 10 | 税率(%)。見積の単位で1つ(§4) |
| `subtotal_yen` | integer | not null default 0 | 税抜の合計(明細の合計) |
| `tax_yen` | integer | not null default 0 | 消費税 |
| `total_yen` | integer | not null default 0 | 税込の合計 |
| `note` | text | NULL 可 | 見積書の備考 |

`estimate_items`
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `estimate_id` | uuid → estimates | not null | |
| `sort_order` | integer | not null default 0 | 並び順 |
| `category` | text | not null default '施工費' | CHECK: 施工費 / 商品代 / 経費 / 値引き(値引きは金額をマイナスで持つ) |
| `description` | text | not null | 内容(例: クロス張替え 量産品) |
| `quantity` | numeric(10,2) | not null default 1 | 数量(㎡ など小数あり) |
| `unit` | text | NULL 可 | 単位(㎡ / m / 式 / 個 / 箇所 / 人工)。段階3 は自由入力+候補 |
| `unit_price_yen` | integer | not null default 0 | 税抜の単価 |
| `amount_yen` | integer | not null default 0 | 税抜の金額 = 数量×単価(端数は §4) |

- **合計は、データベースの関数で明細から計算して保存する**。明細を書き換えるたびにトリガーで再計算する。理由: 画面で計算した合計を信用すると、明細と合計がずれた見積が保存されうる(サーバー側で検証する決まり。共通規約)。
- 提出済・採用・不採用の見積は書き換えない。直すときは版を増やす(「出し直し」ボタンで、いまの版を写した下書きを作る)。理由: 発注元に出した金額を後から追えるようにする。
- 見積を「採用」にできるのは、1つの案件で同時に1つまで。

### 3.5 `costs`(原価)
| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `case_id` | uuid → cases | not null | |
| `category` | text | not null | CHECK: 外注費 / 材料費 / 経費 |
| `description` | text | not null | 内容(例: クロス職人 2人工)。外注先は屋号までにし、個人名は書かない |
| `amount_yen` | integer | not null default 0 | 税抜。仕入の税の扱いは税理士の範囲なので持たない |
| `cost_date` | date | not null default current_date | |
| `memo` | text | NULL 可 | |

- 粗利 = 請求の税抜の合計 − 原価の合計(案件ごと。ビューで出す)。請求がまだの案件は、採用した見積の税抜の合計で「見込みの粗利」を出す。

### 3.6 いまのテーブルに足す列
| テーブル | 足す列 | NULL | 説明 |
|---|---|---|---|
| `jobs` | `case_id` uuid → cases | NULL 可 | 施工を案件につなぐ。旧データは移すときに埋める(§8) |
| `invoices` | `case_id` uuid → cases | NULL 可 | 同上 |
| `invoices` | `estimate_id` uuid → estimates | NULL 可 | どの見積から引き継いだか |
| `invoices` | `invoice_no` text | NULL 可 | 例 `S2026-0018` |
| `invoices` | `due_date` date | NULL 可 | **入金の期日**。発注元の支払条件から初期値を出し、人が直せる |
| `invoices` | `tax_rate_pct` integer | NULL 可 | NULL は「旧データ(内訳なし)」 |
| `invoices` | `subtotal_yen`・`tax_yen`・`total_yen` integer | NULL 可 | 同上。新しい請求ではすべて埋める(§4.3) |
| `clients` | `closing_day` integer | NULL 可 | 締め日(1〜28、0 は月末) |
| `clients` | `pay_month_offset` integer | NULL 可 | 何か月後に払われるか(翌月=1) |
| `clients` | `pay_day` integer | NULL 可 | 支払日(1〜28、0 は月末) |

- `invoices` の金額の列を NULL 可にする理由: 既存の行に、意味の無い 0 を入れないため。計算に使う場所(ビュー)では必ず `coalesce(total_yen, amount::integer)` で受ける(db-change 原則3 の「NULL を必ず受ける実装」の側に寄せる)。
- `payments` は変えない。入金の行は請求にぶら下がったまま。
- 期日の初期値の例: 管理会社A(架空)が「月末締め翌月10日払い」なら `closing_day=0, pay_month_offset=1, pay_day=10`。9月20日の請求の期日は10月10日になる。

### 3.7 監査ログ・権限・RLS
- 監査トリガー `log_entity_changes()` を新しいテーブル(`buildings`・`units`・`cases`・`estimates`・`estimate_items`・`costs`)にも張る。`audit_logs.entity_type` の CHECK に6つを足す(migration_003 と同じ手順)。
- `estimate_items` は行の数が多いので、監査ログが膨らむ。見積が下書きのあいだの明細の変更も記録するかどうかを PM に聞く(§10 の8)。PL の案は「すべて記録する」(PoC の規模では問題にならない)。
- GRANT は `authenticated` に `select, insert, update` のみ。`anon` には何も与えない。DELETE は与えない(migration_002 の default privileges で、新しいテーブルにも DELETE は付かない。適用後に `role_table_grants` で確かめる)。
- RLS は v1 と同じく、ログインした人は全件を読み書きできる(`using (true)`)。1つの事業者で使う前提で、従業員ごとの権限は範囲外。
- `doc_counters` は画面から直接書かせない(関数 `next_doc_no()` だけが書く。`security definer`)。

### 3.8 採番(案件・見積・請求の番号)
- `doc_counters(doc_type text, year integer, last_no integer, primary key (doc_type, year))` を置く。
- 関数 `next_doc_no(doc_type)` が `insert … on conflict … do update set last_no = last_no + 1 returning last_no` を1回の文で実行し、`K2026-0042` の形の番号を返す。
- 理由: 印刷会社向け PoC の「insert のあと update で番号を付ける」形は、2つの処理に分かれていて途中で失敗すると番号の無い行が残る(`reuse-printing-poc.md`)。1つの文で済ませる。
- 番号は取り消しても詰めない(欠番は残る)。年は暦年で始める。決算月で区切るかは PM に聞く(§10 の7)。

### 3.9 ビュー(画面はビューの決まった列だけを読む)
すべて `security_invoker = on`(v1 と同じ。RLS を素通りさせない)。

| ビュー | 1行の単位 | 主な列 | 使う画面 |
|---|---|---|---|
| `case_overview` | 案件 | 案件番号、物件名、部屋番号、発注元、受付日、`status`、`display_status`(8つ)、採用した見積の税込合計、請求の税込合計、入金合計、未入金、原価合計、粗利(または見込み)、最も早い未入金の期日、`needs_invoice`(完了したのに請求が無い)、`is_overdue`(期日を過ぎた未入金がある) | 案件の一覧、物件の画面 |
| `receivables` | 未入金が残る請求 | 請求番号、案件番号、物件名、部屋番号、発注元、請求日、期日、請求の税込、入金済み、残り、期日までの日数(過ぎたらマイナス) | 未入金の一覧 |
| `building_overview` | 物件 | 物件名、住所、種類、部屋数、案件数、進行中の案件数、未入金の合計、最後の施工日 | 物件の一覧 |
| `estimate_reference` | 見積 | 見積番号、版、案件、物件、部屋、状態、提出日、税抜の合計、明細の行数 | 見積の画面の「前回の見積」 |

- `display_status` の決め方: 失注 → 失注。請求があり、入金が請求に届いた → 入金済。請求がある → 請求済。それ以外は `status`。
- 未入金の計算は請求ごと(D65 の現場単位の相殺を、v2 では起こさない)。過入金の請求は「入金済」として扱い、他の請求とは相殺しない。

### 3.10 発注元が複数にまたがる場合(決めつけない。実ヒアリングで確かめる)
例: 管理会社の物件の仕事を、FC 本部を経由して受け、請求は本部に出す。

| | 案1: 案件に2つの列 | 案2: 案件と発注元の関係を表で持つ |
|---|---|---|
| 形 | `cases.client_id`(請求先)+`cases.via_client_id`(経由・元の管理会社。NULL 可) | `case_parties(case_id, client_id, role)`。role は 請求先 / 経由 / 物件の管理 など |
| 良い点 | 単純。一覧のフィルターがそのまま書ける | 3社以上の関わりや、役割の追加に耐える |
| 弱い点 | 3社以上は表せない | 一覧・集計のクエリが重くなる。画面の入力が増える |
| 確かめること | 「経由」が1社で足りるか。請求先と物件の管理会社が違う案件が月に何件あるか | 役割の種類と、それぞれで何を集計したいか |

- **段階2 では `client_id`(請求先)だけで始める。** 案1 の列は、PM の判断で段階2 に入れても後から足してもよい(NULL 可なので、あとから足しても壊れない)。
- 実ヒアリングで聞くこと: 「本部経由の仕事で、物件の管理会社はどこか知っているか・記録したいか」「請求先と、仕事の指示をする相手が違うことがあるか」。

### 3.11 `business_profile`(見積書・請求書に載せる自分の情報)
- 1行だけのテーブル: 屋号、住所、電話、適格請求書発行事業者の登録番号(任意)、振込先の表記(自由記述)。
- 見積書の印刷(段階3)に要る。**登録番号と振込先は秘密ではないが、扱いを PM に確認する**(§10 の9)。研修では架空の値にする。

## 4. 金額と税(PM メモ2)

### 4.1 決まり
1. 明細の単価・金額は**税抜の整数の円**で持つ。
2. 税率は**見積・請求の単位で1つ**持つ(`tax_rate_pct`、初期値 10)。軽減税率の品目は扱わない前提(原状回復・リフォームでは想定しにくい。違ったら版を分ける)。
3. 消費税は**税抜の合計に対して1回だけ**計算する。明細ごとに税を計算して足すことはしない。
   - 参考: 国税庁は、適格請求書の消費税額の端数処理を「1つの請求書につき税率ごとに1回」とし、切り上げ・切り捨て・四捨五入のどれを選ぶかは任意としている。(国税庁 Q&A 問57 https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/pdf/qa/57.pdf 。2026-10-03 に検索結果の要旨で確認。PDF の本文は取得していない。**PM の確認を求める**)
4. 明細の金額(数量×単価)は、数量が小数のときだけ端数が出る。ここの端数も、税と同じ方針で処理する。

### 4.2 端数の方針(PM が決める)
| 案 | 消費税 | 明細(数量×単価) | 良い点 | 弱い点 |
|---|---|---|---|---|
| **切り捨て(PL の推奨)** | 1円未満を切り捨て | 同じ | 発注元にとって不利にならない。請求書でよく見る形で、説明しやすい | 事業者側が最大で1円少なく受け取る |
| 四捨五入 | 四捨五入 | 同じ | 誤差が偏らない | 発注元の計算とずれたとき、どちらに寄せたかの説明が要る |
| 切り上げ | 切り上げ | 同じ | 事業者が損をしない | 発注元に問われやすい |

- 方針は `business_profile` に1つ持つか、コードの定数にするかも決める。PL の案は「定数で始め、発注元ごとに違うと分かったら発注元に持たせる」。

### 4.3 新旧の整合(いまの `invoices.amount` は numeric(12,2))
- `amount` は残す。新しい請求では、アプリが `amount = total_yen`(税込)を同時に書く。理由: 本番の旧画面(台帳・地図の色)が `amount` を読んでいるため。
- 旧データ(移す前の20件)は、`amount` を**税込の請求額**とみなす。`total_yen = amount::integer` を入れ、`subtotal_yen`・`tax_yen`・`tax_rate_pct` は NULL のままにする(「内訳なし」と表示)。
  - 理由: いまの登録画面は「請求額」を1つ入れる形で、税の内訳を聞いていない。請求書に書いた額をそのまま入れたと読むのが自然。
  - 小数の値が無いことを、移す SQL の前に `select count(*) from invoices where amount <> trunc(amount)` で確かめる(0件のはず。架空のデータは整数)。
- 入金(`payments.amount`)も numeric(12,2) のまま。比べるときは整数に丸めず、`numeric` 同士で比べる。
- 集計(発注元別・月次)は税込で出す(v1 と同じ)。粗利だけは税抜で出す(原価が税抜のため)。画面の表の見出しに「税込」「税抜」を必ず書く。

### 5.2 案件の一覧 `/cases`
- 列: 案件番号、物件・部屋、発注元、受付日、状態(ラベル1つ)、金額(採用見積または請求の税込)、気づき(「請求が未作成」「期日超過 3日」などの文字)。

- フィルター: 状態(複数選択)、発注元、物件、受付月、気づき(請求が未作成 / 期日超過)、語句(物件名・部屋・依頼内容)。
- 上に「要対応」の数を出す: 請求が未作成 n件、期日超過 n件。押すとそのフィルターがかかる。
- 並び: 初期は受付日の新しい順。列の見出しで並べ替え。
- スマホ幅では表を**カード**に切り替える(DESIGN §4.1)。

### 5.3 未入金の一覧 `/receivables`
- 並び: **期日の早い順**(期日の無い請求は最後に「期日未設定」としてまとめる)。
- 区切り: 期日超過 / 今週 / 今月 / それ以降 / 期日未設定。
- 列: 期日、残りの日数(または超過の日数)、発注元、案件・物件、請求の税込、入金済み、残り。
- 入金の記録はこの画面から行える(v1 の入金フォームを使う)。消し込みを決めるのは人。
- 上に合計: 未入金の合計、そのうち期日超過の合計。

### 5.4 物件の詳細 `/buildings/[id]`
- 頭: 物件名、種類、住所、ふだんの発注元、メモ。地図は置かない(D80)。
- **部屋ごとの履歴**: 部屋番号ごとに、案件(受付日・状態・内容)、見積(番号・版・税抜の合計)、施工(日付・工種・内容)を新しい順に並べる。部屋なしの案件は「物件全体・共用部」の段にまとめる。
- 「この部屋で案件を登録」ボタン(物件と部屋を入れた状態で `/cases/new` を開く)。

### 5.5 見積の編集 `/estimates/[id]`
- 左(PC)/上(スマホ): 明細の表。行の追加・並べ替え・削除(下書きのあいだだけ)。小計・税・合計は、保存のたびにサーバーが計算した値を表示する。
- 右(PC)/下のタブ(スマホ): **前回の見積と施工**。出す順は次のとおり。
  1. 同じ部屋の過去の見積と施工
  2. 同じ物件の他の部屋の見積と施工
  3. 同じ発注元の直近の見積
  - 各見積に「この明細を写す」ボタンを置く(行ごと、または全部)。写した見積は `copied_from_id` に残る。単価をそのまま使うかどうかは人が決める。
- 状態の操作: 下書き → 提出済(提出日を入れる)→ 採用 / 不採用。提出済の後は「出し直し(版を増やす)」。
- 採用した見積から「請求を作る」: 明細の合計と税率を写した請求の下書きを作る。金額と期日を人が確かめて登録する。

### 5.6 案件の登録・施工の記録(現場でスマホ1分)

## 11. 段階4 への持ち越し(D85)
- **請求を取り消すときの入金の扱い**: v1 では、請求を取り消しても、ぶらさがる入金は生きたまま残る(予行演習で、取り消し済みの請求にぶらさがる入金が1件見つかった)。段階4 で「**入金がある請求は、先に入金を取り消すまで取り消せない**」を既定の案として決める。一緒に取り消す案は、入金という事実を巻き添えで消すので採らない方向。

## 12. 段階4 への持ち越し(D87): `sites` への依存と複製のトリガーを外す
- 段階2 は、v1 のビュー(`invoice_ledger`・`site_status`)と `jobs.site_id`・`invoices.site_id` の NOT NULL を変えないために、**案件ごとに `sites` 行を1つ持つ**(案A)。物件名・部屋番号・発注元・集客経路は `sites` に複製され、トリガー(`cases_before_write`・`cases_sync_site`・`buildings_sync_sites`・`units_sync_sites`・`force_case_site`)で同期している。
- 段階4 で台帳を案件経由に作り直すとき、次の順で外す(expand/contract の contract): ①台帳・集計のビューを `cases`・`buildings`・`units` から読む形にする ②`sites` を読む画面(`/sites/[id]` など)を案件の画面に替える ③同期のトリガーと `force_case_site` を外す ④`jobs.site_id`・`invoices.site_id` を NULL 可にして、`cases.site_id` と `sites` への依存を外す(戻しのバックアップを取ってから)。

## 13. 段階3 で決まったこと(D94〜D97)と、実ヒアリングで確かめること
- **金額**: 明細は税抜の整数円。金額 = 数量×単価(0 方向に切り捨て)、税 = 小計×税率/100(0 方向に切り捨て・小計に1回)。**DB のトリガーが計算して保存**し、画面から書いた合計は上書きされる(migration_008)。値引きは画面では正の金額で入れ、保存のときに符号を反転する。
- **提出済の見積は直せない**(DB が断る)。直すときは「出し直し」で版を増やす(同じ番号・版+1)。採用は1案件に1つ。新しい版があるとき、古い版は採用できない。採用・不採用を提出済に戻せるのは、請求が付いていないあいだだけ。
- **見積から請求**: 採用の見積だけ。金額(税込)と税率は DB が見積から写して固定する(あとから直せない)。1見積=1請求。分割請求は段階4 で決める。
- **粗利は税抜**(D94-1): 売上(税抜)− 原価(税抜)。売上の根拠は 請求(見積由来の請求の小計)/ 見込み(採用した見積の小計)/ 内訳なし(見積に結びつかない請求がある。税込から逆算しない)/ 未定。原価は税抜の整数円で、税込の領収書から計算する補助(10%・8%・切り捨て)を付けた。
- **事業者情報**: 1行だけ(`business_profile`)。研修では架空の値(登録番号は `T0000000000000`)。
- **実ヒアリングで確かめること(D94-4)**:
  - 原価は、税込と税抜のどちらで考えているか(領収書が税込のことが多いという見立ては未確認)。
  - 免税事業者か課税事業者か(登録番号を見積書に載せるか。仕入の税の扱い)。
  - 見積を出し直すことは多いか(版を増やす流れが実態に合うか)。1つの案件に複数の見積(案A・案B)を持つことはあるか。
  - 分割請求(頭金・中間金)は、どのくらいあるか(段階4)。
