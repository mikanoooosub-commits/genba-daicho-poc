作成: アーキテクト(PM依頼) / 最終更新: 2026-09-24

## 0. 前提: これは何のコピーか

`poc-app/` は本番運用中の `flyer-tracker`(チラシ配布実績管理アプリ)のコードのコピー。
**本番の `flyer-tracker` 側は一切変更しない**。このコピーを、原状回復・内装リフォームの
小規模事業者向け「現場を軸にした台帳(地図つき)」に改造する。

既存のテーブル(`schools`/`locations`/`visits`/`visit_logs`/`profiles`/`map_notes`/
`location_pin_status`)・画面(`/`地図・`/list`一覧・`/schools`マスタ)は**削除・改名しない**
(db-changeスキルの append-only 原則)。新しいテーブル・画面を追加する形で対応する。
既存の花見(チラシ配布)向けナビゲーションを残すか外すかは「9. 未決事項」に記載。

## 1. 目的

月末に発注元(管理会社・FC本部)ごとに形式の違う請求書を作り、通帳とExcelを見比べて
入金を確認する作業を、現場(物件)を起点にした1つの台帳に置き換える。前回の施工内容・
負担区分の根拠(経過年数)を、現場ごとにすぐ照会できるようにする。

**初手PoCで狙う効果は2つだけ**:
1. 月末の請求・報告(発注元別の突合)にかかる時間を減らす
2. 前回施工の照会にかかる時間を減らす

**負担区分の判断・金額の確定・請求内容の承認・入金督促するかどうかの判断は人に残す**
(framework.md の昇格順ガード。判断が濃い工程はAIに渡さない)。

## 3. 初手の範囲(やる/やらない)

### やる(2週間PoC)
- 直近3か月分の現場・施工・請求・入金データの取り込み(発注元4社・請求書4パターン)
- 現場→施工→請求→入金を一本につないだ台帳の整備(データ構造化のみ、判断は含まない)
- **①地図画面**(現場ごとの施工履歴・最新状態でピン色分け)
- **②台帳画面**(発注元別・集客経路別の請求・入金の一覧・集計、月次の締め)
- 案件→請求→入金の突合の**下準備**(未入金候補の一覧を出す。確定するのは人)
- 発注元マスタ・ログイン(既存Supabase Authを流用)

### やらない(初手では)
- 負担区分・金額の判断、請求内容の確定(見積・請求書そのものの自動作成)
- 請求書の自動発行(既製の請求アプリ・本部システムと競合しない。台帳から転記して繋ぐ)
- 給与計算・社保手続き(P-D、別候補)
- 労務費内訳つき見積の下書き(P-B、昇格ロードマップへ)
- 完了報告の下書き・現場メモの構造化(**LLM機能。次段**。§8参照)
- 反響トラッキング(チラシ配布→問い合わせの追跡。チラトラ本体の機能で、集客〜入金の
  一本化に昇格するときに検討)
- 複数事業者(テナント)での共用、事業者ごとのデータ分離(§9で判断を求める)

## 4. データモデル

### 4-1. チラトラの既存テーブルの読み替え表

| チラトラのテーブル/ビュー | 本PoCでの扱い | 理由 |
|---|---|---|
| `schools` | **残すが本PoCでは使わない**。削除しない(append-only) | チラシ配布ドメインの対象小学校マスタで、現場台帳ドメインとは無関係。既存機能を壊さないために温存する |
| `locations` | **残すが本PoCでは使わない**。新設の `sites` を代わりに使う | 「配布場所」と「現場(物件)」は概念が異なり、列の意味(spot=立ち位置 等)も転用しにくい。改名ではなく新テーブルで対応(db-change原則1) |
| `visits` | **残すが本PoCでは使わない**。新設の `jobs` を代わりに使う | `rating`(good/normal/bad)の構造は流用したいが、「配布履歴」と「施工履歴」は列が異なる(工種・写真・担当 等)。新テーブルで対応 |
| `visit_logs` | **残すが本PoCでは使わない**。新設の `audit_logs` が jobs/invoices/payments をまとめて記録 | 監査ログの型(create/update/delete + before/after jsonb)はそのまま踏襲。対象エンティティが3つに増えるため、`entity_type` を持つ1本のテーブルに一般化した(3テーブルに分けるより実装・参照が楽) |
| `profiles` | **そのまま流用**。`jobs.user_id` / `audit_logs.user_id` から参照する | メンバー(誰が記録・変更したか)の表示は共通の仕組みでよい |
| `map_notes` | **残すが本PoCでは使わない** | 汎用メモ機能は今回のスコープに必須ではない。将来、現場の目印用に転用も検討可(§9) |
| `location_pin_status`(ビュー) | **残すが本PoCでは使わない**。新設の `site_status` ビューが代わりにピン色を決める | 「直近の配布評価」から「現場の請求・入金状況」へ、ピン色の意味そのものが変わるため新設 |

### 4-2. 新設テーブル

実体は `supabase/schema_poc.sql`。全テーブルに `is_deleted`(論理削除)・
`created_at`/`updated_at` を持つ(chirotra と同じ運用)。

| テーブル | 主な列 | 備考 |
|---|---|---|
| **clients**(発注元) | `name`・`type`(管理会社/FC本部/マッチング/紹介/その他)・`format_memo`(様式メモ) | 発注元マスタ画面から登録 |
| **sites**(現場) | `client_id`・`building_name`・`room_no`・`address_memo`・`lat`/`lng`・`lead_source`(本部紹介/自前チラシ/管理会社/紹介/マッチング/その他) | **入居者名・発注元担当者名の列は作らない**(§8のデータ最小化方針)。地図のピンの単位 |
| **jobs**(施工) | `site_id`・`job_date`・`work_type`・`content`・`assignee_name`・`photo_urls`(配列)・`rating`(仕上がり/手応え)・`memo` | `visits`の構造を踏襲。担当はログインアカウントを持たない外注もいるため自由記述の `assignee_name` を持つ(記録した人=`user_id`とは別) |
| **invoices**(請求) | `site_id`・`amount`・`format_pattern`・`issue_date`・`memo` | **1請求=1現場を初手の前提とする(★要検証)**。`client_id`は持たず`sites.client_id`から導出(二重管理によるズレを避ける)。実態が複数現場をまとめた月次請求なら、`invoice_jobs`等の中間テーブルへexpand/contractで拡張する(§9) |
| **payments**(入金) | `invoice_id`・`payment_date`・`amount`・`reconciliation_status`(unmatched/matched/disputed) | 分割入金・過入金にも対応できるよう1請求に複数行を許す |
| **audit_logs**(監査ログ) | `entity_type`(jobs/invoices/payments)・`entity_id`・`action`・`before_data`/`after_data`(jsonb) | `visit_logs`のパターンを3エンティティに拡張。トリガー1本(`log_entity_changes`)を共通化 |

### 4-3. 新設ビュー(公開契約。db-change原則6)

| ビュー | 用途 | 主な出力列 |
|---|---|---|
| **site_status** | 地図のピン色決定(①画面) | `site_id`・`latest_job_date`・`latest_rating`・`status`(未請求/請求済_未入金/入金済) |
| **invoice_ledger** | 台帳画面(②画面)・発注元別/経路別/月次の集計の元データ | `invoice_id`・`site_id`・`building_name`・`client_id`・`client_name`・`client_type`・`lead_source`・`amount`・`issue_date`・`issue_month`・`paid_amount`・`payment_status`(未入金/一部入金/入金済) |

台帳画面・集計クエリはこの2ビューだけを select する(`select *` は使わず必要な列のみ)。
内部テーブル(`invoices`/`payments`等)を直接JOINするクエリを画面側に増やさない
(内部構造を変えてもビューの形さえ保てば画面側は壊れない)。

| # | 画面 | パス(案) | 主な機能 |
|---|---|---|---|
| ① | 地図 | `/`(既存の地図タブを差し替え) | 現場ピンを `site_status.status` で色分け(未請求=グレー/請求済_未入金=黄/入金済=緑、目安)。ピンクリックで吹き出しを開き、その中の「詳細へ」で現場詳細へ(WO-006差し戻し1)。地図クリックで現場を新規登録(既存の `createLocationAtAction` と同じ操作感)。**(WO-006・D51)** 地図は補助。上部の検索(建物名・住所メモ・部屋番号の部分一致)で現場を引き、一致一覧から現場詳細へ進む。吹き出しに前回施工の日付・工種・内容先頭20字。**(PL-001・D71)** 建物名が完全一致で座標が30m以内の現場は1本のピンにまとめる(色=メンバーのうち最も要対応の状態[請求済・未入金>未請求>入金済]、2室以上は部屋数バッジ、吹き出し=部屋の一覧で6室以上は先頭5室+「ほか N 室」)。建物名が空の現場・離れた同名建物はまとめない |
| ② | 現場詳細 | `/sites/[id]` | 施工履歴の一覧(日付・内容・写真・仕上がり評価)・前回施工日の表示・施工の登録/編集・請求の一覧(その現場分)。**(WO-006)** 「同じ建物の他の部屋」(建物名完全一致・削除済み除く。部屋番号・前回施工日・工種つきで一覧、各現場詳細へ進める) |
| ③ | 台帳 | `/ledger` | `invoice_ledger` を発注元別・集客経路別・月次で集計表示。未入金候補の一覧。請求・入金の登録/編集 |

**入力の粒度**: 現場でスマホ1分。施工登録は「現場を選ぶ→日付・工種・写真・一言メモ」の
最小項目で完了できることを優先し、必須項目を増やさない。

## 6. 集計

台帳画面(③)は `invoice_ledger` を以下の軸で集計する(SQLの `group by` またはアプリ側の
集計。件数が少ない前提のPoCなので、どちらでもよいが**ビューの列を group by するだけで
済む形**にし、専用の集計ビューは増やさない):

- 発注元別(`client_id`/`client_name`)の売上合計・入金合計・未入金合計・月次
- 集客経路別(`lead_source`)の売上合計・入金合計・未入金合計・月次
- 月次(`issue_month`)の全体合計

未入金候補 = `invoice_ledger` で `payment_status <> '入金済'` の行。督促するかどうかの
判断は人が行う(§1)。

## 8. LLM(生成AI)の使用範囲 — 初手ではLLM不要

`poc-candidates.md`(D34)の線引きをそのまま引き継ぐ。**本PoC(台帳+地図+集計)の中核は
LLMを使わない**、通常のDB処理(Next.js Server Actions + Supabase)で組む。

LLMを使うのは次段の2箇所だけ(**今回の実装スコープ外**):
1. 完了報告の下書き(施工記録→発注元の様式に沿った文章)
2. 現場メモ(LINE・音声)→施工記録の項目への整理

実装するときの線引き(先出しで明記。実装者は覚えておく):
- APIに送るのは工事内容・部位・写真の説明文・日付まで
- **物件の住所・部屋番号・入居者名・発注元の担当者名はAPIに送らない**(台帳側で結合する)
- 下書きは必ず本人が画面で直してから使う(「AIは間違えます。だから直す前提で作りました」)
- プロバイダは資料上は特定しない(「一般的な生成AIのAPI」とだけ記載する)。実装コストの
  観点では過去PoC(放デイ)と同じOpenAI APIの流用が最小コスト
- `OPENAI_API_KEY`(導入する場合)はサーバー(`app/api/**`)側でのみ使用し、クライアントに
  一切渡さない(共通CLAUDE.md方針)

## 9. RLS方針

既存(`schema.sql`)を踏襲する。

- 認証済み(`authenticated`)ユーザーのみアクセス可。`anon`には一切権限を付与しない
- 単一事業者・少人数チームでの共有・相互編集を前提とし、行ごとのユーザー分離はしない
  (誰でも見て編集できるが、`audit_logs`で必ず追跡できる)
- `jobs`/`invoices`/`payments`は物理DELETE権限を付与しない(論理削除のみ)
- `audit_logs`への書き込みはトリガー(`security definer`)経由のみ。クライアントからの
  直接INSERTは許可しない

詳細は `supabase/schema_poc.sql` のRLS/GRANT節を正とする。

## 10. 受入条件(テスト役が使う)

### ①地図画面
- [ ] 現場ピンが地図上に表示され、`site_status.status` に応じて色分けされる
- [ ] ピンをクリックすると、その現場の施工履歴(日付・内容・写真・仕上がり評価)が確認できる
- [ ] 地図クリックで新規現場を登録でき、発注元・集客経路を選べる
- [ ] 論理削除された現場・施工はピン・履歴に出てこない
- [ ] 同じ建物・近い位置(30m以内)の現場は1本のピンにまとまり、色は最も要対応の状態、吹き出しに部屋の一覧が出る。1室だけの現場は従来の吹き出し(PL-001)

### ②現場詳細
- [ ] 施工の登録・編集ができ、写真・工種・担当・仕上がり評価を保存できる
- [ ] 前回施工日と内容がひと目で分かる(照会に時間がかからない)
- [ ] その現場の請求一覧(状態つき)が確認できる

### ③台帳
- [ ] 発注元別・集客経路別・月次で売上・入金・未入金が集計表示される
- [ ] 未入金候補(`payment_status <> '入金済'`)が一覧できる
- [ ] 請求・入金の登録・編集ができ、金額は0以上の数値のみ受け付ける
- [ ] 請求・入金を訂正すると`audit_logs`に記録が残り、誰がいつ何を変えたか追跡できる

### ④発注元マスタ
- [ ] 発注元の追加・編集ができ、種別(管理会社/FC本部/マッチング/紹介/その他)を選べる
- [ ] 発注元に紐づく現場が1件以上あるとき、発注元を削除できない、または論理削除で扱う

### ⑤ログイン
- [ ] 既存のログイン機能がそのまま動作する(変更していないため回帰なし)

### 共通(セキュリティ)
- [ ] 未認証(anon key)で新規テーブルを直接叩くと拒否される(401/42501)
- [ ] `jobs`/`invoices`/`payments`への物理DELETEリクエストが拒否される(DELETE権限なし)

## 12. PMに判断を求める点

以下は勝手に決めず、PMの判断を仰ぐ。雛形・初期案は作ったが、実装には反映していない。

1. **請求の粒度**: 「1請求=1現場」を前提に `invoices.site_id` を必須にした(§4-2)。
   実態が「発注元ごとに複数現場をまとめた月次請求」であれば、`invoice_jobs`のような
   中間テーブルへの拡張(expand/contract)が必要。ヒアリング(§8のH2)で確認してから
   決める。
2. **既存のチラシ配布ドメイン画面(`/list`・`/schools`)の扱い**: そのまま残してナビゲー
   ションに残すか、今回のPoC期間中は非表示にするか。残すとデモ時に「これは何のアプリ
   か」が伝わりにくくなる懸念がある一方、隠すと元のチラトラの実績(自己紹介の材料)が
   見えなくなる(`poc-candidates.md`「今すぐ」の使い方)。
3. **入金の取消・訂正の運用**: `payments`に論理削除(`is_deleted`)を用意したが、金額を
   間違えて登録した場合に「削除して入れ直す」のか「マイナス行を足して相殺する」のか、
   会計的にどちらが実態に合うか(税理士との整合)を確認していない。
4. **`invoices`のステータス列を持たせるか**: 今回は請求書自体の状態(下書き/確定/取消)
   を列として持たず、入金額との比較で状態を導出する設計にした(§4-3の`payment_status`)。
   請求書の確定・取消というワークフロー自体が必要なら、別途状態列の追加を検討する。
5. **デモ表示モード**: 既存アプリは`demo`スキーマで本番と分離したデモ表示を持つが、本PoC
   用のデモモードが必要かは未確認(`schema_poc.sql`冒頭コメント参照)。必要なら
   `demo`スキーマにも同じDDLを当てる(db-change原則8)。
6. **複数事業者(テナント)での共用**: 現状は単一事業者・単一チーム前提のRLS(§9)。
   将来、複数の顧客企業にこのPoCを展開する場合は`tenant_id`列とポリシーの拡張が必要。
7. **写真の保存先**: `jobs.photo_urls`は文字列配列としたが、実際のアップロード先
   (Supabase Storageか、既存の管理会社アプリへのリンクのみ保持するか)は未検討。
8. **地図ピンの色の具体的な配色**: `site_status.status`(未請求/請求済_未入金/入金済)を
   どの色に割り当てるかはUI実装時に決める(poc-design.html §4では「緑=入金済・黄=
   請求済未入金・グレー=未請求、等は要件定義時に確定」と保留のまま)。
