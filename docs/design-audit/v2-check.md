**気づいた点(PL が追加で見たもの)**
- **次の一手の決め方が、D106-1(決定済み)と食い違う。** 提案は 完了=請求を作る / 請求済=「入金を待つ」(操作なし)/ 入金済=済み。決定は **請求済=「入金を登録」を主にする**(最終の一手が隠れていた問題を、C-1 の導線修正で直したばかり)。「入金を待つ」では押す所が無い。
- **完了の「請求を追加」が、金額の手入力のほう**(A-2・B-2・C-2 の主ボタン)。採用済みの見積があれば、主は「この見積から請求を作る」にした(導線修正)。3案ともこの区別が無い。
- 詳細のスマホは、状態が「完了」の1パターンしか描かれていない。依頼・施工中・請求済の主ボタンの出し分けは未設計。
- B の橙のボタンは、白地・地との境目が 2.1:1(1.9:1)。**墨の 2px の枠で形を出している**(枠を外すと基準を割る。Claude Design 自身が明記)。
- B・C の数字の太さ 800 は、Windows の游ゴシックでは 700 に落ちる。画像より細く見える。
- C は、PC の左メニューを上の横メニューに、画面の地を紙の色にした。**提案資料から一番離れる**(C 自身の記述)。
- フォーカスの輪は未確認(C の紙の地では黄が見えにくい)。実機の書体も未確認。

## 3. PL の見立て(判断は PM・ユーザー)
1. **Claude Design の推し(B をベースに、一覧と見積の PC は A の表組みを混ぜる)に賛成。** 理由は、LP での見栄えと「次の一手・お金」が最も強い案が B で、見比べの弱点(カード)を A の表で補えるため。
2. ただし採る前に、**次の3点を決める**:
   - (a) 次の一手の決め方を D106-1 に合わせる(請求済=入金を登録。完了で採用済みの見積あり=この見積から請求を作る)。
   - (b) 欠けた文言(状態の自動の注記、原価の案内)を戻す。
   - (c) 橙は「枠つき」を条件に採る。
3. **段階的に入れる提案**(全面の差し替えは、研修の前日に壊すリスクが高いので、以下の順):
   1. 見積(スマホ)の「合計を上に固定+保存・提出を下に固定」と、見積(PC)の保存・提出を上の同じ場所に(前に見つけた導線の欠陥が直る。部品は小さい)
   2. 一覧の「次の一手」の列と、詳細の「次にやること」の札(色は足さない=A 相当)
   3. 一覧・詳細の B の面(深緑の面+大きい数字)と橙の次の一手(トークンの追加が要る。コントラストと枠の確認つき)
   4. 登録(スマホ)の大きなタイルと要約の帯
4. **実装は、生成 HTML を貼らず、いまの部品(`v2.css` 系)に当てはめる**(クラスは B の提案の切り方を参考に)。
