- 「現場=建物名+部屋」で、建物の上位がない。同じ建物は名前の一致と位置の近さで寄せている(D71)。

- コードの約3割が使われていないチラシ配布アプリの残りで、読む人を迷わせる。

## 2. 3つの案

### 案A: いまのコードに継ぎ足す(main のまま、少しずつ足す)
- やり方: いまの画面とテーブルを残し、物件・案件・見積の画面とテーブルを横に足していく。入口を地図から一覧に変えるのは最後。
- 手間: 段階1〜4 の合計で、案B より 2〜3 割多いと見ている。旧画面と新画面の両方を、データのつながりを保ったまま直し続けるため。
- 危険:
  - 継ぎ足しのたびに本番が変わる。研修の前に崩れる危険がいちばん高い。
  - 「現場」と「部屋」が両方ある状態が長く続く。同じ物件を2か所で直すことになり、二重入力という PoC の弱点そのものを再現する。
  - チラシ配布アプリの残りは消せない(`poc-app/CLAUDE.md` §1)ので、読みにくさは続く。
- 残るもの: 認証・監査・RLS・デプロイはすべてそのまま。

### 案B(PL の推奨): 同じリポジトリの `rebuild` ブランチで、アプリの層を組み直す
- やり方:
  - `poc-app` のリポジトリに `rebuild` ブランチを切る。画面と部品は新しい設計(SPEC-v2・DESIGN)で作り直す。
  - 土台(認証・Supabase の接続・zod の作法・監査トリガー・論理削除・デプロイ手順)はそのまま使う。
  - チラシ配布アプリのコードと文書は、このブランチで外す(後述の「PM に決めてほしいこと」①)。
- データベース: **同じ Supabase プロジェクトの `public` スキーマに足す**(下の 3. で比べた結果)。いまのテーブルは消さず、列も消さない。新しいテーブルと、いまのテーブルへの NULL 可の列を足す。
- 本番との関係:
  - main と本番(genba-daicho-poc.vercel.app)は、段階ごとの受入まで今のまま。
  - `rebuild` ブランチは Vercel のプレビュー URL で見る。Vercel のログイン保護がかかるので、PM とユーザーが見る方法は段階1 で決める。
  - 受入が済んだ段階から main に入れる。
- 手間: 段階1〜4 で、案A より少ない見込み。画面を作り直す分は増えるが、旧画面との両立を考えなくてよい分が大きい。
- 危険:
  - データベースは本番と共有になる。足すだけ・NULL 可にしておけば、本番の画面は壊れない(db-change の原則1・2)。
  - いまのテーブルに足す列(`case_id` など)を新しい画面から書いた場合、本番の旧画面にもその行が見える。施工・請求・入金はいまの形のまま書くので、旧画面の表示は崩れない。
  - ブランチが長く main から離れる。main に入る小さな修正(PL が直すもの)は、その都度 `rebuild` に取り込む。
- 残るもの: 認証・監査・RLS・GRANT・デプロイの考え方とコード。監査ログは1本のテーブル(`audit_logs`)に新旧の変更がまとまって残る。

### 案C′: 新しいリポジトリで作り、Supabase は同じプロジェクトをスキーマで分ける
- やり方:
  - 新しいリポジトリ(例: `genba-daicho-v2`)と、新しい Vercel プロジェクトを作る。
  - Supabase は今と同じプロジェクトを使う。新しいスキーマ `v2` を作り、テーブルをそこに置く。
  - 新しい Supabase プロジェクトは作らない。無料枠の2つ目はもう別の用途で使っている(PM メモ 2026-10-03)。
- 手間: 案B より多い。
  - リポジトリ・Vercel・環境変数・ドメインの設定をやり直す。
  - `v2` スキーマを API に出す設定(Supabase の Exposed schemas。ユーザーの操作)が要る。
  - GRANT・RLS・監査トリガーも `v2` 用に書き直す。
- 危険:
  - 監査ログが `public.audit_logs` と `v2.audit_logs` の2本に分かれる。
  - いまのデータ(架空の13現場など)を、スキーマをまたいで写す SQL が要る。
  - 本番のアプリが2つになる。どちらを見せるかを、毎回決めることになる。
- 残るもの: 認証は同じ Supabase のユーザーを使えるので、ログインの仕組みは引き継げる。
- 良い点: チラシ配布アプリの残りから完全に切れる。LP に載せるときに「一から作った」と言いやすい。

## 3. データベースの持ち方: `public` に足すか、`v2` スキーマに分けるか

PM メモ1 に沿って、案B・案C′ のどちらでも選べる2つを比べた。

| 観点 | `public` に足す | `v2` スキーマに分ける |
|---|---|---|
| アプリからの使い方 | 今のまま。設定は要らない | Exposed schemas への追加が要る(ユーザーの操作)。クライアントで `db: { schema: 'v2' }` を指定する。いまの `server.ts` にはデモ用にスキーマを切り替える処理があり、それと同じ形でできる |
| 監査ログ | 既存の `audit_logs` とトリガー関数をそのまま使える(`entity_type` の CHECK を広げるだけ) | `v2` に作り直す。関数を共有するなら、スキーマ名の扱いを書き直す |
| いまのデータとのつながり | 施工・請求・入金に `case_id` を足すだけで、新旧の画面が同じ行を見る | 写すか、スキーマをまたいで参照する。二重管理になりやすい |
| 戻しやすさ | 戻しの SQL は「足した列とテーブルを外す」 | `drop schema v2 cascade` 1行で消せる(ただし物理削除。戻しの手段としてだけ使う) |
| 名前の衝突 | 新しいテーブル名(`buildings`・`units`・`cases`・`estimates`・`estimate_items`・`costs`)は、いまのテーブル名と重ならないことを確認した | 起きない |
| 読む人への分かりやすさ | 新旧のテーブルが同じ場所に並ぶ。`sites` を「旧」と明記する必要がある | 分かれていて分かりやすい |

**PL の推奨: `public` に足す。**
理由: 監査ログを1本に保てること(「直した履歴を必ず追える」は PoC の核。`poc-app/CLAUDE.md` §4)と、新旧の画面が同じ施工・請求・入金の行を見られることを重く見た。`v2` スキーマの分かりやすさは、文書と命名で補う。

## 4. 比べた結果(まとめ)

| | 案A 継ぎ足す | **案B ブランチで組み直す** | 案C′ 新リポジトリ+`v2` |
|---|---|---|---|
| 段階1〜4 の手間 | 多い(両立のため) | **中** | 多い(環境を作り直す) |
| 本番を止めない | △ 継ぎ足すたびに本番が変わる | **○ 受入まで main は今のまま** | ○ |
| 二重入力の弱点を引きずらない | × | **○** | ○ |
| 認証・監査・RLS・デプロイ | そのまま | **そのまま** | 作り直し(認証は共有) |
| 監査ログの一本化 | ○ | **○** | × 2本 |
| チラシ配布アプリの残り | 残る | **外せる(要判断①)** | 無い |
| LP での見せ方 | 弱い | **作り直したと言える** | いちばん言いやすい |

**PL の推奨は案B+`public` に足す。** 決めるのは PM とユーザー。

## 5. 案B を選んだ場合の進め方

1. `rebuild` ブランチを切る(段階1 の最初のコミット)。
2. チラシ配布アプリのコードと文書を外す(①が「外す」になった場合)。
   - 外すものは 1. の表の「残り」と「文書」。消す前のファイルは git の履歴に残るので、戻せる。
   - `supabase/schema.sql` などチラシ配布アプリの SQL は、本番の DB に適用されていない。ファイルは残し、`supabase/legacy-flyer/` に移すことを提案する。
3. 段階ごとに、SQL は番号つきのファイル(`migration_005_…`)と戻しの SQL を作る。適用はユーザーが行う。
4. 新しい画面がそろうまで、旧画面(現場の詳細・台帳)は `rebuild` ブランチにも残す。**地図は D80 で外した(Leaflet とともに撤去)。**段階2 で案件の一覧ができたら入口を一覧に替え、旧画面は「旧台帳」としてメニューの奥に下げる。段階4 の受入で、外すか残すかを決める。
5. 段階ごとに次を行う。
   - tsc・lint・build を通す。
   - 受入条件をテストする(`docs/test-scenarios.md`)。
   - `docs/change-log.md` と `docs/architecture.md` を更新する。

## 6. PM とユーザーに決めてほしいこと

1. **案A / 案B / 案C′ のどれにするか**(PL の推奨は案B)。
2. **データベースの持ち方**: `public` に足すか、`v2` スキーマに分けるか(PL の推奨は `public`)。
3. **チラシ配布アプリの残りを `rebuild` ブランチで外してよいか**。
   - `poc-app/CLAUDE.md` §1 は「既存の画面・テーブルは削除・改名しない」と定めている。これは「チラシ配布アプリの実績として残す」ための決まりだった。
   - 本番 DB にはチラシ配布アプリのテーブルが無く、画面も転送で閉じている。そのため、残す実益は小さいと PL は見ている。
   - 外すなら、§1 を「本番のテーブルは消さない。チラシ配布アプリのコードは外してよい」に改める必要がある(この CLAUDE.md の改訂は段階1 で PL が行う。PM の承認が要る)。
4. **`rebuild` ブランチのプレビューを誰がどう見るか**(Vercel のログイン保護の扱い)。
